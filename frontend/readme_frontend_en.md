# Frontend

## Purpose
Contains the complete Vue.js 3 application of the Real-Estate-Maintenance-Optimizer (calendar view, appointment creation, route optimization).

## Technologies
Vue.js 3, PrimeVue 4, Vue.cal (calendar view), Vue Router, Axios, Leaflet (appointment map on the overview page, and later the basis for the planned route optimization)

## Folder Structure

### `public/`
Static files copied as-is by the build process, e.g. `favicon.ico`, `index.html`, or static images. These files are not bundled. Assets that are imported or reused in code do not belong here; they belong in an assets folder under `src/`.

### `src/`
Root directory of the actual application source code, split into:

- **`components/`** – Reusable UI building blocks (e.g. buttons, cards, form fields, calendar widgets) used across multiple views. One component per file, filename in PascalCase (e.g. `AppointmentFormDialog.vue`). No business logic or direct API calls inside components; use `composables/` or `services/` instead. App-wide layout building blocks live in `components/layout/` (e.g. `AppHeader.vue`, `AppFooter.vue`, `NavigationMenu.vue`), calendar building blocks live in `components/calendar/` (`AppCalendar.vue` wraps `vue-cal`, alongside `CalendarToolbar.vue`, `CalendarDayHeader.vue`, `CalendarEventCard.vue`), appointment create/detail building blocks live in `components/appointments/` (`AppointmentFormDialog.vue`, `AppointmentDetailDrawer.vue`, `AppointmentPropertySelect.vue`, `AppointmentMaterialInput.vue`, `AppointmentAiSuggestionBanner.vue`), property-list building blocks live in `components/properties/` (`PropertyList.vue`, `PropertyCard.vue`, `PropertyCreateCard.vue` for the pinned "add property" card, `PropertyFormDialog.vue` for its creation dialog, `PropertyLocationPreviewMap.vue` for the dialog's Leaflet location preview), the daily appointment overview's building blocks live in `components/overview/` (`DailyAppointmentList.vue`, `DailyAppointmentCard.vue`), and the map building blocks live in `components/map/` (`AppointmentMapCard.vue` for the card frame, `AppointmentMap.vue` wraps Leaflet).
- **`views/`** – Pages / route targets of the application, e.g. appointment overview, appointment creation, material planning. One view per route, filename usually suffixed with `View` (e.g. `CalendarView.vue`). Views orchestrate components and should contain as little own logic as possible.
- **`router/`** – Central configuration of Vue Router: route definitions, mapping to views, navigation guards, and lazy-loading. One central `index.ts`/`index.js` as the entry point, routes with descriptive `name` attributes.
- **`services/`** – Axios-based API clients for communicating with the Spring Boot backend as well as with external services. One service per business domain (e.g. `versionService.ts`, `appointmentService.ts`, `propertyService.ts`, `geocodingService.ts` for address resolution via the OpenStreetMap Nominatim API), plain modules with one exported async function per operation.
- **`stores/`** – Global state management, e.g. the loaded appointments and which create/detail overlay is open (`stores/appointments.ts`, the first real use of Pinia in this app — needed because the header's "+Termin" button and the calendar overlay must act on the same state, which a plain composable can't share across mount points) and the loaded properties plus which property create dialog is open (`stores/properties.ts`, shared between the "Immobilien" list, the pinned create card, and the appointment form's "Objekt" dropdown, mirroring `stores/appointments.ts`'s create-dialog pattern). No direct API access inside a store, use `services/` instead.
- **`composables/`** – Reusable Vue Composition functions encapsulating reactive logic needed across multiple components or views. Naming convention `useXxx` (e.g. `useCalendarNavigation`, `useCalendarAppointments`, `useAppointmentDeleteConfirmation`, `usePropertyAppointmentSummaries`, `useTodaysAppointments`, `useAppointmentMapMarkers`), contains pure logic without UI rendering.
- **`types/`** – Hand-written TypeScript types (e.g. `appointment.ts`, `property.ts`) plus ambient shims for untyped packages (e.g. `vue-cal-shims.d.ts` for `vue-cal`, which ships no type declarations of its own).
- **`utils/`** – Small, reusable, framework-agnostic helper functions (e.g. locale-aware date formatting, `appointmentSchedulingOptions.ts`'s day/time/duration/recurrence option generators) that are not tied to Vue's reactivity system and therefore don't belong in `composables/`.
- **`i18n/`** – Central `vue-i18n` setup; creates and exports the app's i18n instance, merging all locale message bundles from `locales/`.
- **`locales/`** – Translation message files for static UI text, split into `de/` (active default locale) and `en/` (fallback locale), one JSON file per feature namespace (e.g. `header.json`, `footer.json`, `appointments.json`). See `CLAUDE.md`, Coding Conventions, for the rule that all other identifiers stay in English.
- **`styles/`** – Component styles extracted from `.vue` files, referenced via `<style scoped src="...">`, mirroring the `components/` folder structure (e.g. `styles/layout/` for `components/layout/`, `styles/calendar/` for `components/calendar/`, `styles/appointments/` for `components/appointments/`, `styles/properties/` for `components/properties/` and `views/PropertiesView.vue`, `styles/overview/` for `components/overview/`, `styles/map/` for `components/map/`).
- **`__tests__/`** – Vitest unit tests (component, composable, service and store tests), one spec file per source file, plus a shared `setup.ts` (polyfills `window.matchMedia`, which jsdom lacks but PrimeVue's overlay components call on mount).

### `e2e/`
Playwright end-to-end tests (e.g. `navigation.spec.ts`, `calendar.spec.ts`, `appointments.spec.ts`, `overview-map.spec.ts`, `properties.spec.ts`), run via `npm run test:e2e`. The appointment and property flows need the backend running locally (`mvn spring-boot:run` in `backend/`), since Playwright's `webServer` config only starts the frontend dev server; `overview-map.spec.ts` additionally mocks the Nominatim requests via route interception, so the test does not depend on a real external geocoding call. `properties.spec.ts` creates a property against the real backend and removes the JSON file `PropertyFileRepository` wrote for it under `backend/ExampleObjects/` afterwards, since there is no delete endpoint yet to clean up through the API (see `backend/readme_backend_en.md`, section "`ExampleObjects/`").

### `package.json`
Dependencies and build/start scripts.

## Implemented Features

- **Layout:** the application header and footer (`components/layout/`). The footer is a narrow, black, fixed bar pinned to the bottom of the viewport (`App.vue` wraps header/content/footer in a flex column with `min-height: 100vh`), showing a copyright notice and the backend-reported version, and is responsive like the header.
- **Navigation:** the four main navigation entries (Overview/`Übersicht`, Calendar/`Kalender`, Statistics/`Statistik`, Properties/`Immobilien`) each route to a dedicated view under `views/`. `OverviewView.vue` renders the daily appointment overview (see below), `StatisticsView.vue` currently renders only a localized placeholder sentence via the reusable `components/ViewPlaceholder.vue`, `CalendarView.vue` renders the calendar, and `PropertiesView.vue` renders the property list (see below). `NavigationMenu.vue` renders its links as `RouterLink`s (active entry highlighted via `router-link-exact-active`), and the header logo/brand name links back to the overview page.
- **Daily appointment overview (overview page):** `OverviewView.vue` renders `components/overview/DailyAppointmentList.vue`, a list of only today's appointments from the shared `stores/appointments.ts` (derived via the `useTodaysAppointments` composable, which filters by calendar day and sorts ascending by start time, so the first list entry is the next upcoming and the last is the day's final appointment). Each appointment appears as a numbered `DailyAppointmentCard.vue` with time, title, property/address, materials, and its distance and duration (`{km} km · {duration}`, computed from `travelDistanceKm` and `end - start` — an actual travel-time figure like the one the planned route optimization (Feature 6) will provide does not yet exist in the data model); clicking a card opens the same globally-mounted `AppointmentDetailDrawer.vue` used by the calendar and property list. The list ends with the same `AppointmentAiSuggestionBanner.vue` already used in the appointment form, shown purely for decoration (currently non-functional). With no appointments scheduled for the current day, the view shows a localized empty-state message.
- **Appointment map (overview page):** `OverviewView.vue` renders `components/map/AppointmentMapCard.vue` to the left of `DailyAppointmentList.vue`, a Leaflet map (`components/map/AppointmentMap.vue`) showing today's appointments as numbered markers connected by a line in chronological order. The `useAppointmentMapMarkers` composable ties this into `useTodaysAppointments` and `stores/properties.ts`: each appointment first uses its property's stored coordinates (`Property.latitude`/`longitude`); only when those are missing does `services/geocodingService.ts` fall back to the backend's own `GET /api/geocode` endpoint (a browser cannot reliably call Nominatim directly, see `backend/readme_backend_en.md`, section "Address Geocoding"). The map automatically zooms to fit every marker on load and whenever the appointment list changes (`fitBounds`), while still allowing manual zooming via Leaflet's built-in controls (buttons, scroll wheel, pinch). Addresses that cannot be resolved even through the fallback are skipped without crashing and flagged with a subtle hint.
- **Calendar:** `CalendarView.vue` renders `components/calendar/AppCalendar.vue`, a `vue-cal` 4.10.2-based day/week/month/year calendar (dark theme, custom toolbar with a localized date-range title, previous/today/next navigation and a view switcher, plus per-day appointment-count/travel-distance headers via the `weekday-heading` slot and colored per-category event cards via the `event` slot). Sundays are hidden in every view via `vue-cal`'s `hide-weekdays` prop, since the company does not schedule appointments then. Navigating to `/calendar` always shows today in the week view, since the view/date state lives in `CalendarView`'s component instance and is re-initialized fresh on every mount (no `keep-alive`). `useCalendarNavigation` wraps view switching, previous/next/today (delegated to vue-cal's exposed instance methods, since `selectedDate` has no `v-model`) and locale-aware range-title formatting; `useCalendarAppointments` converts `Appointment` domain objects into vue-cal events and per-day summaries, reading from the shared `stores/appointments.ts` Pinia store rather than owning its own state.
- **Appointments (create/read/move/delete/mark completed):** the header's "+Termin" button and clicking a calendar event both act on the shared `stores/appointments.ts` Pinia store — needed because a plain composable can't share one instance across the globally-mounted header button and the calendar overlay. Two route-less overlays are mounted once at `App.vue` level: `AppointmentFormDialog.vue` (a PrimeVue `Dialog` with title/property/description/day/time/duration fields, whose day dropdown does not offer Sundays as an option in the first place for the same operational reason (`generateUpcomingDayOptions` in `utils/appointmentSchedulingOptions.ts`), an "unverschiebbar" toggle, a "Dauerauftrag" toggle with a repeat-interval selector, a material tag input, and a static, non-functional AI-suggestion banner) and `AppointmentDetailDrawer.vue` (a PrimeVue `Drawer` with badges, description, material checklist, history log, an inline reschedule form hidden when the appointment is locked, and a delete action that asks whether to remove a whole recurring series via `useAppointmentDeleteConfirmation` and PrimeVue's `ConfirmationService`). `AppointmentPropertySelect.vue`'s "Objekt" dropdown reads from the shared `stores/properties.ts` Pinia store rather than hardcoded example data.
  - Every PrimeVue `Select` in these two overlays sets `input-id` (not `id`) so its `<label for>` stays associated with the field once a value is selected — a plain `id` lands on the Select's non-interactive outer wrapper, and PrimeVue overrides the focusable combobox's accessible name with the selected value, breaking the label link.
  - **Completed status:** `AppointmentDetailDrawer.vue` shows a "Mark as completed" button for a not-yet-completed appointment (sets `actualEnd` to the current time via `store.completeAppointment()`), and for a completed one a "Completed" badge with the time plus a button to revert it (`store.reopenAppointment()`). The calendar (`useCalendarAppointments.ts`) renders a completed appointment's block up to its actual end (`actualEnd`) instead of its originally planned end — shorter if the job finished early, longer if it ran over — and marks it with the additional `calendar-event--completed` CSS class (a muted grey, `styles/calendar/calendar-event-card.css`) instead of its category color. The appointment itself stays at its original start time on the calendar.
- **Objects Overview ("Objekte Auflisten"):** `PropertiesView.vue` renders `components/properties/PropertyList.vue`, a responsive CSS-grid list (`auto-fill, minmax(260px, 1fr)`) of `PropertyCard.vue` cards fetched from the backend-backed `stores/properties.ts`, pinned first behind a `PropertyCreateCard.vue` (a card-styled button with a large plus icon). Each `PropertyCard.vue` shows the property's icon (a PrimeIcons class from its `icon` field), name, address, and its open/completed appointment counts plus next upcoming appointment — all three derived from the shared `stores/appointments.ts` via the `usePropertyAppointmentSummaries` composable (filtered by `propertyId`, "next" meaning the earliest not-yet-completed appointment whose start is still in the future), not stored on the property itself. Clicking the next-appointment link opens the same globally-mounted `AppointmentDetailDrawer.vue` used by the calendar. Editing/deleting properties is not yet implemented.
- **Creating a property:** clicking `PropertyCreateCard.vue` calls `stores/properties.ts`'s `openCreateDialog()`, which drives the globally-mounted `PropertyFormDialog.vue` (mounted once at `App.vue` level, mirroring `AppointmentFormDialog.vue`'s pattern) — a PrimeVue `Dialog` with a name field, three separate address fields — street and house number (both required) plus an optional address supplement (e.g. "a") — recombined client-side into a single `"<street> <houseNumber><supplement>"` line, and postal-code/city fields (`POSTAL_CODE_PATTERN` requires exactly 5 digits); only the combined line is ever sent to or stored by the backend, which still treats `address` as one opaque string. As the address fields change, a 500 ms debounce geocodes the combined address via `services/geocodingService.ts` and shows the resolved position as a single marker in `PropertyLocationPreviewMap.vue`, a small, non-interactive Leaflet map (`dragging`/`scrollWheelZoom` disabled, since it is a read-only preview, not the appointment map). Submitting calls `stores/properties.ts`'s `createProperty()`, which posts to the backend and appends the result to the shared property list; the property's coordinates are only sent along if the preview already resolved them, otherwise the backend stores `null` and the appointment map's existing geocoding fallback resolves them later, exactly as for the seeded example properties.
- **Not yet implemented:** account management (only a non-functional placeholder with example dropdown data), editing/deleting properties, route/distance calculation, and location-based automatic scheduling.
