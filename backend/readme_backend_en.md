# Backend

## Purpose
Contains the complete Spring Boot application of the Real-Estate-Maintenance-Optimizer (REST API, appointment logic, road routing, AI appointment optimization, rent payment check; AI-supported duration estimation planned).

## Technologies
Java 25 (LTS), Spring Boot 4, Spring Security, JJWT (JSON Web Token), Spring Data JPA, Flyway, PostgreSQL (appointments, objects & user/auth; Supabase in production), Testcontainers, LangChain4j with `langchain4j-anthropic` (Claude Haiku 4.5 for the AI appointment optimization, Claude Haiku 5.5 for the rent payment check)

### Objects Overview ("Objekte Auflisten")
`PropertyController`/`PropertyService`/`PropertyRepository` expose the same properties selectable when creating an appointment (`AppointmentPropertySelect.vue` on the frontend) as a list for the "Immobilien" page, plus a `POST /api/properties` create endpoint used by the pinned create card there, a `PUT /api/properties/{id}` update endpoint (`PropertyService.update` keeps the existing id and icon and overwrites name, address and coordinates) used by each card's edit button, and a `DELETE /api/properties/{id}` endpoint that also deletes every appointment referencing the property (via the `ON DELETE CASCADE` foreign key from `appointments.property_id`) as well as its apartments and tenants (see "Apartments & Tenants"). A created property always gets the default icon `pi-building` (the create form has no icon field) and, unless the frontend already resolved coordinates via live geocoding while the form was open, `latitude`/`longitude` are stored `null` and resolved later through the same fallback the appointment map already uses. Every `PropertyResponse` carries `tenantCount`, the number of tenants living in the property's apartments: `PropertyService.listAll` loads it for all properties of the account with a single grouped query (`TenantRepository.countTenantsPerPropertyByOwnerId`, returning `PropertyTenantCount` projections; a property without tenants counts as 0) and the single-property lookups use `TenantRepository.countByApartmentPropertyId`; it is derived, not stored on `Property`. Open/completed appointment counts and each property's next appointment are not stored on `Property` either; the frontend derives them from the already-loaded appointments (filtered by `propertyId`) for the property statistics, so no aggregation endpoint was needed.

### Apartments & Tenants
`ApartmentController`/`ApartmentService`/`ApartmentRepository`/`TenantRepository` store the apartments of a property and their tenants. A property has any number of apartments and an apartment any number of tenants, including none: an `Apartment` (floor, living area in m², `totalRent`, `coldRent` and `additionalCosts`) belongs to exactly one property and exists on its own, so a vacant apartment stays when its last tenant is deleted; its `Tenant`s (first and last name) share one set of apartment data instead of duplicating it. Ownership follows the property: apartments and tenants are only reachable through a property of the logged-in account (`findByIdAndPropertyOwnerId`, `findByIdAndApartmentPropertyOwnerId`), another account's data behaves as if it did not exist (`404`).

- **Endpoints:** `GET /api/properties/{propertyId}/apartments` lists the apartments sorted by floor, then by the last name of their first tenant (tenants sorted by last and first name, vacant apartments with an empty tenant list); `POST` on the same path creates an apartment, vacant or with a first tenant (`ApartmentWithTenantRequest`: `apartment` and an optional `tenant`); `PUT /api/apartments/{apartmentId}` edits the apartment data shared by all its tenants (`ApartmentUpdateRequest`: `apartment` and an optional `rentEffectiveMonth`, see below); `DELETE /api/apartments/{apartmentId}` deletes the apartment with its tenants, their payments and its rent history; `POST /api/apartments/{apartmentId}/tenants` adds a tenant to an apartment; `PUT /api/tenants/{tenantId}` renames a tenant (`TenantDetailsRequest`); `DELETE /api/tenants/{tenantId}` deletes the tenant, the apartment staying even without a tenant and the tenant's payments staying as payments of the former tenant. Every endpoint that returns a body answers with the (updated) `ApartmentResponse`.
- **Rent changes:** when an edit changes `totalRent`, the new rent applies from `rentEffectiveMonth` (`YYYY-MM`, default the current month, from January 2000 up to the current month, otherwise `400` with `rentPayment.error.invalidRentMonth`) and earlier months keep the rent they had. `ApartmentService` remembers the rent before the first change in `apartments.initial_rent`, drops every recorded change from that month on (`ApartmentRentChangeRepository.deleteFrom`) and records the new rent in `apartment_rent_changes`; the rent payment check judges every month by the rent due in it (see "Rent Payment Check"). An unchanged rent records nothing and ignores the month.
- **Validation:** names must not be blank and at most 50 characters; the floor lies between -3 and 100 (0 is the ground floor, negative numbers are basement levels); the area is greater than 0 and at most 99999.99; the three rent figures are at least 0, at most 9999999.99 and have at most two decimals. `totalRent` ("Mietpreis") is stored independently of `coldRent` and `additionalCosts`, not derived from them. Anything else is a `400`.
- **Limits:** a property may have at most 500 apartments and an apartment at most 10 tenants (`ApartmentService.MAX_APARTMENTS_PER_PROPERTY`/`MAX_TENANTS_PER_APARTMENT`); exceeding them raises `TenantLimitExceededException` (carrying the exceeded limit, which fills the `{0}` of the localized message), answered with a `409`. Adding and deleting tenants and editing or deleting an apartment lock the apartment row (`findByIdAndOwnerIdForUpdate`), so concurrent changes of one apartment cannot exceed the tenant limit or mix up its rent history. Demo accounts are additionally limited to 10 tenants in total (see "Authentication & Account Binding"), exceeding that answers a localized `403`; a vacant apartment does not use up a tenant creation, and they are not seeded with tenants.
- **Deleting:** deleting a property or an account removes its apartments and tenants through the `ON DELETE CASCADE` foreign keys of migration `V5`.

### Appointment Conflict Detection
Before creating or moving an appointment, `AppointmentService.create()` and `AppointmentService.move()` share one check (`AppointmentService.requireFreeSchedule`) of whether the requested schedule overlaps with, or comes closer than the configured buffer to, an already existing, not-yet-deleted appointment of **the same account** — scoped to the account (`ownerId`) alone, regardless of property (`propertyId`); two appointments of different accounts at the same property and time remain unrestricted, since location-based planning (Feature 3) does not exist yet. An appointment already marked as completed only blocks up to its actual end (`actualEnd`) instead of its originally planned end, since an appointment finished early genuinely frees up the time after it. For a recurring series, only the requested (first) appointment is checked for conflicts, not each of the 12 occurrences materialized afterwards; conflict-checking each individual occurrence, as well as a conflict check on update (`PUT /api/appointments/{id}`), are deliberately out of scope and can be picked up as a follow-up issue. On a conflict, creating or moving is rejected with `AppointmentConflictException`/`409` (nothing is persisted or changed, and a demo account's creation limit is not consumed); the exception carries the earliest free start at or after the originally requested start at which the requested duration is free of any conflict (`AppointmentService.findNextAvailableStart`, repeated until no conflict remains), which `GlobalExceptionHandler` returns as an `AppointmentConflictResponse` (a localized `message` plus `suggestedStart`/`suggestedEnd`).

The **buffer time** is one global setting, `remo.appointments.buffer-minutes` in `application.yml` (default `5`, bound by `AppointmentSchedulingProperties`; a negative value or one above 1440 fails the startup; `0` disables the buffer), and applies account-wide just like the overlap check, not per appointment or property. Every other appointment's occupied range is widened by the buffer on both sides (`AppointmentService.isTooCloseTo`), so a requested schedule is a conflict when it overlaps with that widened range, and the suggested next free slot starts at least the buffer after the end of the appointment it follows. A real overlap and a buffer violation are answered with the same message, since the buffer is part of what "free" means. `move()` first rejects a locked appointment, then reuses the same check but ignores the moved appointment itself, so it can be shifted partly onto its own previous time, and skips the check entirely for an unchanged schedule, so a neighbour that already lies within the buffer (e.g. created via update, which is not checked) never blocks a no-op move. Each regular account may override this default with its own buffer (`users.appointment_buffer_minutes`, set via `PUT /api/account/appointment-buffer`, see "Authentication & Account Binding"); `AppointmentService.requireFreeSchedule` resolves it per request via `AppointmentSchedulingProperties.bufferMinutesFor`, so the configured value only applies to accounts without their own setting.

### Address Geocoding
`GeocodingService` resolves addresses to coordinates via the OpenStreetMap Nominatim API, for the appointment map on the frontend overview page (see `frontend/readme_frontend_en.md`). The call runs **server-side** instead of directly from the browser because Nominatim's abuse detection blocks requests lacking a real, application-identifying `User-Agent` header — one a browser can never set itself for security reasons. `RestClientConfig` provides the `RestClient.Builder` for this; `GeocodingService` sets a project-identifying `User-Agent` (pointing at the GitHub repository, no personal data), caches results per address in memory, and throttles new requests to one per second (Nominatim's usage policy); a failed request is logged and falls back to an empty result rather than surfacing as an error, since geocoding is an optional enhancement (see "Error Handling & Robustness" in `.claude/rules/error-handling.md`). If the full address has no match, the service retries without a trailing city-district suffix (e.g. "Köln-Porz"), since Nominatim's free-text search otherwise fails on such addresses even though the street itself is real, and only then falls back to a structured search by the German postal code it contains. The frontend calls `GET /api/geocode` both as a fallback for properties without stored coordinates and live, debounced, while the "new property" form is open, to show a location preview before submitting.

`GeocodingService.validateAddress()` additionally checks, once on submit of the "new property" form (not on every keystroke, per Nominatim's rate limit), whether the entered street/house-number/postal-code/city combination really exists: a structured Nominatim search with all four fields (only attempted when the postal code is exactly 5 digits, skipped otherwise) is a `MATCH`, but only if Nominatim's own house number and postal code (when it returns them) agree with the ones entered — Nominatim's `postalcode` parameter is only a ranking hint, not a hard filter, and can return the real address with its actual (different) postal code despite a wrong one being entered, which without this check would have been wrongly accepted as a confirmed `MATCH`; if that has no result, a retry without the postal code that resolves to exactly one address, with a matching house number too, yields a `SUGGESTION` with that address's actual street, postal code and city (the common case: an otherwise-unique street with a typo'd postal code); anything else (no result even without the postal code, several results, or a disagreeing house number) is a generic `NOT_FOUND`, without a suggestion, since no single correction can be derived. `PropertyFormDialog.vue` blocks creation on anything but `MATCH` (see `frontend/readme_frontend_en.md`); this is enforced client-side only for now, since `CreatePropertyRequest` stores just the combined `address` string, not its structured components, so the server has nothing to re-validate against on `POST /api/properties`.

### Road Routing
`RoutingService` calculates the road route through an ordered list of stops via the openrouteservice (ORS) directions API (`POST {base-url}/v2/directions/{profile}/geojson`), for the driving distance and time between the day's appointments on the frontend overview page and map (see `frontend/readme_frontend_en.md`). `RoutingController` exposes it as `POST /api/routes` (session and CSRF token required like every data endpoint) with `RouteRequest` (`coordinates`: 2 to 25 `RouteCoordinate`s with `latitude` in ±90 and `longitude` in ±180, none `null`, otherwise `400`; optional `mode`: `CAR` for the ORS profile `driving-car` or `WALKING` for `foot-walking`, `CAR` when omitted, any other value `400`) and answers with `RouteResponse`: `geometry` (the route polyline as `[longitude, latitude]` pairs in GeoJSON order, which the frontend swaps for Leaflet), `distanceMeters`, `durationSeconds` and one `RouteLeg` (`distanceMeters`, `durationSeconds`) per section between two consecutive stops. The call runs **server-side** so the ORS API key (sent in the `Authorization` header) never reaches the browser; the coordinates sent to ORS are ordered `[longitude, latitude]` as ORS expects. Results are neither persisted nor stored in the database (no Flyway migration): `RoutingService` only keeps an in-memory cache per mode and coordinate sequence (emptied once it holds 500 routes), and a cache hit does not consume any ORS quota.

**Configuration** (`remo.routing.*`, `RoutingProperties`, registered by `RoutingService`): `enabled` (default `false`, environment variable `REMO_ROUTING_ENABLED`), `base-url` (`https://api.heigit.org/openrouteservice`), `api-key` (environment variable `REMO_ROUTING_API_KEY`, required: the backend refuses to start while `enabled` is `true` without one, per "Fail Fast" in `.claude/rules/error-handling.md`), `max-requests-per-account-per-minute` (default `20`) and `max-requests-per-minute` (default `30`, across all accounts) and `max-requests-per-day` (default `1500`, across all accounts and within a sliding 24 hours, so a flood of newly created demo accounts cannot exhaust the daily ORS quota). Routing is thus explicitly switchable: with `enabled=false` (e.g. no key locally) the endpoint answers `501` (`RoutingDisabledException`, message `routing.error.disabled`) and the frontend silently keeps showing the straight line, without a hint, since nothing failed. To get a key, create a free account at https://openrouteservice.org/dev/#/signup; as of October 2026 the free plan allows 2,000 directions requests per day and 40 per minute, which the limits above stay below and which apply across both modes. The ORS profile is not configurable but follows from the request's mode. Locally put `REMO_ROUTING_ENABLED=true` and `REMO_ROUTING_API_KEY=...` into `backend/.env` (see `backend/.env.example`); in production the deploy workflow writes `REMO_ROUTING_API_KEY` from the optional GitHub secret of the same name into `backend.env` and sets `REMO_ROUTING_ENABLED` to `true` exactly when that secret is set (without it, the workflow only warns and routing stays off).

**Robustness and degradation:** the per-account and overall per-minute limits and the daily limit are enforced by one `SlidingWindowRateLimiter` each; exceeding a per-minute limit answers `429` (`RateLimitExceededException`, reason `tooManyRouteRequests`, message key `auth.error.tooManyRouteRequests`), exhausting the daily limit answers `429` with reason `routeQuotaExhausted` (message key `auth.error.routeQuotaExhausted`), and a request rejected by a later limit gives back the attempt it had already reserved at the earlier ones. Every failure of the route calculation itself — timeout or connection error (5-second timeout from `RestClientConfig`), any `4xx`/`5xx` answer from ORS (including its own quota `429` and the `404` for a position it cannot route to), an unusable answer or a segment count that does not match the number of stops — is logged via `slf4j` and translated into a `RoutingUnavailableException`, which `GlobalExceptionHandler` maps to `503` with the localized message `routing.error.unavailable`. The service deliberately does not degrade by itself (a route that does not exist would be an incorrect answer, see `.claude/rules/error-handling.md`); the deliberate degradation — drawing the straight line instead and showing a hint — happens in the frontend. `RestClientConfig`'s `RestClient.Builder` bean is `prototype`-scoped so every service gets its own builder: `RoutingService` sets the ORS base URL and API key as default header on it, which with a shared singleton builder could leak into the Nominatim client of `GeocodingService`.

### AI Appointment Optimization
`OptimizationService` (`POST /api/optimizations`) rearranges the logged-in account's appointments to save road distance and driving time. The work is split so that a language model can never produce an invalid move:

1. **Planning window:** only appointments starting at least `min-lead-days` (28) and at most `horizon-days` (365) days from today (zone `remo.optimization.zone`, `Europe/Berlin`) are considered, and only onto days in that window. Locked and completed appointments are never moved; they and every appointment outside the window stay fixed obstacles.
2. **Travel matrix:** `PlanningSnapshotFactory` picks the properties with coordinates that are visited most often in the window (at most `max-matrix-locations`, 50, openrouteservice allows 59), and `DistanceMatrixService` asks the openrouteservice matrix API (`POST {routing base-url}/v2/matrix/driving-car`, same key and switch as "Road Routing") for the driving distance and time between every pair, cached per location set and limited to `max-matrix-requests-per-day` (400); disabled routing answers `501`, a failure `503` exactly like routing. Appointments at a property without coordinates (or outside the matrix) take part only as obstacles, and a day containing such an appointment is neither moved from nor onto, since its route could not be priced and its driving times not checked.
3. **Candidates:** `OptimizationPlanner` (no I/O, indexing the schedule by day so each evaluation only looks at the two affected days) tries every movable appointment on every day of the window that already has appointments at known locations, at the start of the working day (`work-day-start`/`work-day-end`, 07:00–19:00, never on Sundays) and right after or before each appointment of that day, rounded to `slot-minutes` (15). A move is feasible only if it keeps the account's buffer to every appointment **plus the driving time** from the previous and to the next appointment, and a recurring occurrence stays within `max-recurring-shift-days` (14) of the date it was originally planned for (`Appointment.recurrenceAnchorStart`, remembered on its first automatic move, so repeated runs cannot drift it). Its saving is the difference of the affected days' routes (sum of the legs between consecutive appointments, there is no depot) before and after the move; only moves saving at least `min-saved-distance-meters` (500) and no driving time are kept, at most `max-candidates-per-appointment` (3) per appointment and `max-candidates-for-ai` (60) overall, sorted by saved time.
4. **AI selection:** `ai/OptimizationAdvisor` sends these candidates (id, title, property, current and proposed slot, saved km and minutes) to Claude through LangChain4j (`ai/AiChatModelConfig` builds an `AnthropicChatModel` with `remo.ai.model`, default `claude-haiku-4-5`, `timeout` 60 s and one retry). A fixed system prompt asks for a JSON selection (`{"selections":[{"candidateId","reason"}]}`), at most one per appointment, preferring the largest time and distance savings, skipping negligible ones and treating candidate fields as data. The answer is parsed with Jackson; unknown candidate ids, a second selection of the same appointment and overlong reasons (500 characters) are dropped, an empty, non-JSON or failing answer is logged and answered with `503` (`AiUnavailableException`). Without candidates the AI is not called at all.
5. **Re-validation and proposals:** the selections are applied one after another to a copy of the schedule and each is re-checked with the planner, so two selections competing for the same slot cannot both survive. The surviving moves are stored as `PENDING` `OptimizationProposal`s of a new `OptimizationRun`, replacing (expiring) every proposal still pending from an earlier run; no appointment is changed yet. The slow external calls (matrix, AI) run outside any database transaction.

**Confirmation:** `OptimizationProposalService.accept` (`POST /api/optimizations/proposals/{id}/accept`) fetches a matrix of the two affected days outside any transaction and then, under the account's transaction lock, re-validates the move against the current schedule; if the appointment was changed, deleted or the slot is no longer feasible or saving, the proposal becomes `EXPIRED` (kept despite the `409`) and nothing moves. Otherwise `AppointmentService.applyOptimizedSchedule` moves the appointment with the history entry "Moved by the AI optimization from … to …" and the proposal is stored as `ACCEPTED` with the recalculated savings. `reject` only marks it `REJECTED`; deciding twice answers `409`, another account's proposal `404`.

**Savings statistics:** `OptimizationSavingsService` (`GET /api/optimizations/savings?granularity=WEEK|MONTH`, default `WEEK`) sums the accepted proposals' saved distance and driving time in total and per period of their acceptance, with an entry for every week (starting Monday) or month from the first acceptance up to the current one (zero for empty periods). Accepted proposals outlive their appointment (`appointment_id` is set to `NULL` on delete), so the statistics stay complete.

**Configuration and limits:** `remo.ai.*` (`AiProperties`): `enabled` (default `false`, `REMO_AI_ENABLED`), `api-key` (`REMO_AI_API_KEY`, required while enabled, otherwise the backend refuses to start), `model` (`REMO_AI_MODEL`, default `claude-haiku-4-5`), `timeout`, `max-tokens`, `max-runs-per-account-per-hour` (5) and `max-runs-per-day` (200, across all accounts; both answer `429`, reasons `tooManyOptimizations`/`optimizationQuotaExhausted`). A run that never consulted the AI (no candidates, or a failure before the AI call such as a routing error or a used-up demo run) gives both run slots back, and only one run per account may be in flight at a time (otherwise `429`, reason `optimizationInProgress`), so a double click cannot pay for two AI calls. With `enabled=false` a run answers `501` (`ai.error.disabled`) before anything is calculated. The optimization also needs road routing for the matrix. `remo.optimization.*` (`OptimizationProperties`) holds the planning rules listed above; the frontend shows the default values (`utils/optimizationRules.ts`), so a changed lead time, horizon or recurring shift must be changed there too. Locally set `REMO_AI_ENABLED=true` and `REMO_AI_API_KEY` in `backend/.env`; in production the deploy workflow writes the optional GitHub secret `REMO_AI_API_KEY` and enables the AI exactly when it and `REMO_ROUTING_API_KEY` are set. A demo account may start one run (`users.remaining_ai_optimizations`, migration `V7`); it is checked before and used up only once the AI was actually consulted and the result stored, so a failed run or one without candidates keeps it.

### Rent Payment Check
Tenants' rent payments are checked against a bank statement PDF (`RentPaymentController`), per property and only after the check was activated for it. The statement is never stored: it only lives in memory for the duration of the scan request (`spring.servlet.multipart.file-size-threshold` of 6 MB keeps every accepted upload out of temporary files), and only the payments the user confirms are saved. Because Claude reads it, the statement's content is sent to the Anthropic API inside that request — there is no purely local evaluation.

1. **Activation:** the check is off for every property (`properties.rent_tracking_start` is `NULL`) until `PUT /api/properties/{propertyId}/rent-payments/tracking` activates it; it then counts from the first day of the current month, so activating it on 15 January already judges January, and an earlier start is kept. Until then the yearly table only holds `UNTRACKED` months, no alert is raised and scanning or storing payments answers `409` (`rentPayment.error.trackingInactive`). Months before the start stay `UNTRACKED`, also when payments exist for them.
2. **Scan:** `POST /api/properties/{propertyId}/rent-payments/scan` (multipart part `file`) rejects, before the AI is consulted, a switched-off AI (`501`), an unknown or foreign property (`404`), a property without activated check (`409`), an empty file or one that does not start with `%PDF-` (`400`, `rentPayment.error.*`), a file above `remo.payments.max-statement-size` (5 MB, `413`; `spring.servlet.multipart` enforces the same limit earlier and the configured limit is reported even then) and an exceeded scan limit (`429`). `ai/RentPaymentAdvisor` then sends the PDF as a base64 `PdfFileContent` to Claude through the shared LangChain4j chat model, overriding the model per request with `remo.payments.scan-model` (`REMO_PAYMENTS_SCAN_MODEL`, default `claude-haiku-5-5`; set `claude-sonnet-5-5` if the Haiku model cannot read PDFs) and `scan-max-tokens` (8192). A fixed system prompt asks for the incoming payments only as JSON (`{"payments":[{"paymentDate","amount","payerName","reference","periodYear","periodMonth"}]}`) and to treat the document as data. The answer is untrusted: every row is validated (parseable and plausible date, positive amount below 10 million with at most six decimals so an extreme exponent is dropped before any calculation, rent period 1–12 and 2000–2100 else defaulted to the payment date's month, texts trimmed, at most 500 rows, the number of dropped rows is logged) and an unusable answer or a failing model becomes a `503`.
3. **Assignment:** the backend, not the AI, assigns each payer name to a tenant of the property (`TenantNameMatcher`): names are compared as case-, accent- and order-insensitive word sets. A tenant whose first (or its initial) and last name both occur is a `MATCH`, one whose last name alone occurs is `POSSIBLE`; candidates in different apartments stay unassigned (`NONE`), co-tenants of one apartment pick the one with the smallest id since their rent is shared. `alreadyRecorded` flags a payment its apartment already has with the same date, amount and reference. The tenants' names are not sent to the AI.
4. **Confirmation:** `POST /api/properties/{propertyId}/rent-payments` (at most 500 `RentPaymentRequest`s, no `null` entries) stores the confirmed payments as `RentPayment` rows of the tenant's apartment. All tenants are checked first (an unknown or foreign one answers `404` and stores nothing), a payment its apartment already has with the same date, amount and reference is skipped (a unique index on exactly these columns also catches two confirmations arriving at the same time, answering `409`), and the answer is `{"savedCount","skippedCount"}`.
5. **Deleted tenants:** a payment belongs to its apartment, not to the tenant: when a tenant is deleted, `ApartmentService.deleteTenant` first notes their name as `former_tenant_name` (`lastName, firstName`) on their payments and detaches them (`tenant_id` becomes `NULL`), so the payments keep counting for the apartment and are listed in the yearly table as payments of the former tenant; the apartment stays even without a tenant (it then raises no alert, since alerts are listed per tenant). Only deleting the apartment itself removes its payments (`ON DELETE CASCADE` on `apartment_id`).
6. **Rent changes:** an apartment's rent is `Apartment.totalRent`, but when `ApartmentService.updateApartment` changes it, the rent before the first change is kept in `apartments.initial_rent` and the new rent is recorded in `apartment_rent_changes` from the month the user chose (default the current month, replacing every change from that month on; see "Apartments & Tenants"). `RentSchedule` then judges every month by the rent due in it: the rent of the latest change effective in or before that month, or the rent before the first change.
7. **Payment status:** an apartment's rent is judged by the sum of the payments of all its tenants (and former tenants) for that period month (`RentPaymentRepository.sumByApartmentAndMonth...`). `RentStatusCalculator` (no I/O) derives per month `PAID` (paid in full, also in advance), `PARTIAL` (partly paid) or `OVERDUE` (nothing paid) once the due day `remo.payments.due-day` (5, inclusive) has passed, `PENDING` (not fully paid, due day not yet passed, current month only), `UPCOMING` (later months) and `UNTRACKED` (before the activation month, or before the month the apartment was created in if that is later, so a new apartment is not overdue for earlier months; `apartments.rent_tracking_from` is set when an apartment is created). `GET /api/properties/{propertyId}/rent-payments?year=` (default: current year, `400` outside 2000–2100) returns `trackingStart` (`YYYY-MM`, `null` while inactive), one row per tenant with twelve months (status, paid and expected amount), the apartment's current monthly rent and the tenant's alert, and `formerTenantPayments` for the year; co-tenants share their months. The alert level is `OVERDUE` for any tracked `PARTIAL`/`OVERDUE` month, `PENDING` for a pending month, otherwise `NONE`; `GET /api/rent-payments/alerts` lists every tenant of an activated property with an alert (with property and apartment id) so the frontend can mark tenant and property. A tenant without any recorded payment in an activated property is therefore flagged from the due day of the activation month on.
8. **Limits:** `max-scans-per-account-per-hour` (10) and `max-scans-per-day` (200, across all accounts) answer `429` with the reasons `tooManyPaymentScans` and `paymentScanQuotaExhausted`; a scan is only possible while `remo.ai.enabled` is true. Demo accounts may use the check (no creation quota). The `ai.error.*` messages were reworded from "AI optimization" to "AI function" since both features share them.

### Authentication & Account Binding
- **Login:** `POST /api/auth/login` (`AuthService.authenticate`) checks the username (case-insensitive, stored in lowercase) and the password against the BCrypt hash (strength 12) in `users`. An unknown username takes as long as a wrong password (a dummy hash is compared), so usernames cannot be probed. On success, `AuthController` issues an HS256 JWT (`JwtService`, JJWT; issuer `remo`, subject = account id, session start in milliseconds, expiry after `remo.auth.session-duration` = 8 h) and sets it as cookie `remo_session` (`SessionCookieManager`: `HttpOnly`, `SameSite=Strict`, `Path=/api`, `Secure` unless `remo.auth.cookie-secure=false`), so JavaScript can never read the token.
- **Every request:** `JwtAuthenticationFilter` only authenticates when signature, issuer and expiry are valid, the account still exists, has not expired (demo) and the session was not revoked by a later logout (`users.sessions_valid_from`). `SecurityConfig` is stateless and only permits `GET /api/version` (health checks), `POST /api/auth/login|demo-account|logout` and `/error`; everything else, including `/api/geocode` and `/api/routes` (so the Nominatim proxy and the openrouteservice quota cannot be abused anonymously), answers `401` without a valid session.
- **CSRF:** since the session is a cookie, every state-changing request additionally needs the CSRF token (Spring Security `csrf().spa()`, double submit): the readable cookie `XSRF-TOKEN` (`SameSite=Strict`, written on every response by `CsrfCookieFilter`) has to be echoed as header `X-XSRF-TOKEN`, which axios does automatically. CORS (`CorsConfig`) allows credentials only for `remo.frontend.base-url`.
- **Brute-force protection:** `SlidingWindowRateLimiter` (in memory, per backend instance, at most 10,000 tracked keys with least-recently-used eviction) allows 5 failed logins per username *and* client address and 20 per client address within 15 minutes, then answers `429`. Every attempt is reserved atomically before the (deliberately slow) BCrypt check, so parallel requests cannot slip past the limit; a successful login gives its reservation back. Keying the username limit by client address too means nobody can lock another client out of an account (e.g. the owner of `account_default`); distributed guessing is bounded by the per-client limit, BCrypt's cost and the minimum password length. The client address is taken from `X-Forwarded-For` only when a local/private reverse proxy sets it (`server.forward-headers-strategy: native`). **Deployment requirement:** the reverse proxy in front of the backend (e.g. nginx) must forward the real client address (`proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`), otherwise every client shares the proxy's address and the per-client limits apply to all users together.
- **Logout:** `POST /api/auth/logout` clears the cookie; for a regular account every session started so far is revoked server-side (on other devices too), a demo account is deleted with all its data.
- **Profile settings:** `AccountService` (`PUT /api/account/*`, regular accounts only; a demo account is rejected with `DemoAccountRestrictedException`/`403`) changes the username (requires the current password like the password change, otherwise `422`; 3–50 letters, digits, `.`, `-`, `_`, not starting with the `demo-` prefix reserved for demo accounts, stored normalized; a name already used by another account is answered with `409`; at most 10 changes per 15 minutes per account, then `429`, so taken names cannot be enumerated; the session stays valid, since the JWT identifies the account by id), the password (requires the current password, otherwise `422`; the new one needs at least 8 characters, at most the 72 bytes BCrypt supports and must differ from the current one, otherwise `400`; wrong current passwords of the username and the password change count against one shared per-account limit of 5 per 15 minutes, then `429`; on success every earlier session is revoked via `users.sessions_valid_from` and `AccountController` issues a fresh session cookie for the current one) and the appointment buffer (0–1440 minutes, stored in `users.appointment_buffer_minutes`, migration `V3`; `NULL` means the configured default). `CurrentUserResponse` carries the effective `appointmentBufferMinutes`.
- **Account binding:** `properties.owner_id` (foreign key to `users`, `ON DELETE CASCADE`) binds every property and, through it, every appointment to exactly one account. All repository queries are owner-scoped, the services take the owner id from `@AuthenticationPrincipal AuthenticatedUser`, and another account's id is answered with `404` rather than `403`, so ids cannot be probed. Creating an appointment for another account's property is rejected the same way.
- **Initial account `account_default`:** migration `V2` creates it (as `debschke`, display name "David Ebschke") without a password and assigns all previously existing data to it. Migration `V4` renames it to `account_default` (display name "Account_Default"), unless its username was already changed in the profile settings; its password hash is kept. `InitialAccountPasswordService` sets its password on startup from `REMO_AUTH_INITIAL_USER_PASSWORD` (at least 8 characters and at most the 72 bytes BCrypt supports; anything else is ignored with a warning instead of failing the startup), only while it has none yet, and stores only the BCrypt hash; the plain password never ends up in the repository, the database or the log. To change it later, set `password_hash` back to `NULL` in the database and restart with the new value.
- **Demo account:** `POST /api/auth/demo-account` (`DemoAccountService`) creates a password-less account `demo-<random>` that expires after one session (8 h). `DemoDataSeeder` fills it with 5 properties in Cologne (with coordinates) and 30 appointments over the next 21 days (three time slots per day, some locked) plus 12 appointments on six working days 35 to about 52 days ahead that pair far-apart properties on one day while the same property recurs on other days, so the AI optimization finds savings. It may start the AI optimization once (`users.remaining_ai_optimizations`, migration `V7`). It may create only 3 more properties, 3 more appointments and 10 tenants (`users.remaining_property_creations`/`remaining_appointment_creations`/`remaining_tenant_creations`, migration `V6`, checked in `PropertyService`/`AppointmentService.create`/`ApartmentService`, where creating an apartment with its first tenant and adding a further tenant each use up one tenant creation while editing and deleting never do; a recurring series counts as one appointment; exceeding the limit answers a localized `403`). It is deleted on logout, otherwise by `DemoAccountCleanupScheduler` (every 15 minutes) once expired. Abuse limits: at most 10 demo accounts per client address and hour and 100 existing at the same time (`429`); creations are serialized by a PostgreSQL advisory transaction lock, so concurrent requests cannot exceed the global limit together, and a creation that fails does not use up one of the client's creations.
- **Configuration:** `remo.auth.*` (`AuthProperties`) in `application.yml`. The secrets come from the environment variables `REMO_AUTH_JWT_SECRET` (required, at least 32 bytes, otherwise the backend refuses to start), `REMO_AUTH_INITIAL_USER_PASSWORD` and `REMO_AUTH_COOKIE_SECURE`; locally optionally from `backend/.env` (git-ignored, imported via `spring.config.import`, see `.env.example`). The deploy workflow writes them from the GitHub secrets `REMO_AUTH_JWT_SECRET` and `REMO_AUTH_INITIAL_USER_PASSWORD` (plus the optional repository variable `REMO_AUTH_COOKIE_SECURE`, default `true`) into `backend.env`.

- **`ai/`** – LangChain4j integration: `AiChatModelConfig` (the Claude chat model bean, only while `remo.ai.enabled` is true), `OptimizationAdvisor` (prompt, answer parsing and filtering of the AI optimization), `AdvisorCandidate` and `AdvisorSelection` (see "AI Appointment Optimization" above). The AI-supported estimation of appointment duration based on similar previous appointments is still planned. `RentPaymentAdvisor` reads the incoming payments off a bank statement PDF through the same chat model (see "Rent Payment Check" below).

### `src/main/resources/`
Application configuration files: `application.yml` (Spring Boot configuration, incl. `spring.messages.basename`, `remo.frontend.base-url`, `remo.auth.*`, `remo.routing.*`, `remo.ai.*`, `remo.optimization.*`, the optional import of a local `.env`, the local `spring.datasource` defaults and the JPA/Flyway settings), `db/migration/` (Flyway migrations, see "Persistence" below) and `locales/` (German/English translations for dynamic, server-generated text via Spring's `MessageSource`: `messages.properties`, `messages_de.properties`, `messages_en.properties`, resolved via `LocalizationConfig`; the base `messages.properties` bundle holds the English texts, matching the English fallback locale). ### Persistence
Properties and appointments are stored in PostgreSQL (replacing the former `ExampleObjects/`/`ExampleTerms/` JSON files; a fresh database starts empty, without seed data):

- **Schema:** all tables live in the dedicated schema `remo` (`spring.flyway.schemas`, `hibernate.default_schema`) rather than `public`, because Supabase automatically exposes `public` through its Data API. Tables: `users` (migration `V2`; later columns via `V3`, `V6` and `V7`), `properties` (foreign key `owner_id` to `users` with `ON DELETE CASCADE`), `appointments` (foreign key `property_id` with `ON DELETE CASCADE`, indexes on `series_id`, `property_id` and `start_at`), `appointment_history_entries`, `apartments` (migration `V5`, foreign key `property_id` with `ON DELETE CASCADE`) , `tenants` (foreign key `apartment_id` with `ON DELETE CASCADE`), `optimization_runs` and `optimization_proposals` (migration `V7`, foreign keys `owner_id` with `ON DELETE CASCADE` and `appointment_id` with `ON DELETE SET NULL`; `appointments.recurrence_anchor_start` added in the same migration), so deleting an account removes all of its data in the database. Row Level Security is enabled on every table without any policy, so Supabase's API roles get no access, while the backend's owning database role is unaffected. `rent_payments` and `apartment_rent_changes` (migration `V8`, which also adds `properties.rent_tracking_start`; `rent_payments.apartment_id` cascades with the apartment, `tenant_id` becomes `NULL` when a tenant is deleted, a unique index keeps identical payments of an apartment out, `amount > 0` and `period_month` 1–12 are check constraints, row level security is enabled like the other tables).
- **Migrations:** Flyway owns the schema (`src/main/resources/db/migration/V<n>__*.sql`, applied automatically on startup); Hibernate only validates it (`ddl-auto: validate`). Never edit an already applied migration, add a new `V<n+1>__...sql` instead.
- **Local development:** `docker compose up -d` in `backend/` starts PostgreSQL 17 (`docker-compose.yml`), matching the defaults in `application.yml` (`jdbc:postgresql://localhost:5432/remo`, user/password `remo`); `mvn spring-boot:run` additionally needs `REMO_AUTH_JWT_SECRET` (and, to be able to log in as `account_default`, `REMO_AUTH_INITIAL_USER_PASSWORD` plus `REMO_AUTH_COOKIE_SECURE=false` for plain `http://localhost`), most conveniently in `backend/.env` (see `.env.example`).
- **Production (Supabase project "RemoDB"):** the backend on the Oracle Cloud instance reads `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD` from the environment (see `.env.example`). Use Supabase's **Session pooler** connection (IPv4-reachable, port 5432, user `postgres.<project-ref>`, `?sslmode=require`), not the direct connection (IPv6-only) nor the transaction pooler (port 6543, incompatible with Hibernate's server-side prepared statements). The deploy workflow writes these values from the GitHub secrets `REMO_DB_URL`, `REMO_DB_USERNAME` and `REMO_DB_PASSWORD` into `backend.env` (mode `600`) next to the deployed jar; the backend's systemd unit loads it via `EnvironmentFile=`. If the database is unreachable, Flyway fails on startup and the deploy's health check fails.
- **Tests:** repository, service and controller tests run against a throwaway PostgreSQL 17 container (Testcontainers, `TestcontainersConfiguration`), so `mvn test` requires a running Docker daemon.
