# Backend

## Purpose
Contains the complete Spring Boot application of the Real-Estate-Maintenance-Optimizer (REST API, appointment logic, route optimization, AI-supported duration estimation).

## Technologies
Java 25 (LTS), Spring Boot 3, Spring Security, JJWT (JSON Web Token), Spring Data JPA, Spring Mail, Flyway, PostgreSQL (appointments & objects, later also user/auth; Supabase in production), Testcontainers, LangChain4j (AI integration)

## Folder Structure

### `src/main/java/com/remo/realestatemaintainceoptimizer/`
Root directory of the actual application source code, split into:

Already present:

- **`controller/`** – REST endpoints of the application, e.g. appointment, material, and route management. One controller per business domain, no business logic inside the controller; use `service/` instead. Currently contains:
  - `VersionController` — `GET /api/version`, reporting the version currently packaged from `pom.xml` via Spring Boot's `BuildProperties` (generated at build time through the `spring-boot-maven-plugin` `build-info` goal, bound to the `generate-resources` phase so it runs before compilation/tests).
  - `AppointmentController` — `GET/POST /api/appointments`, `GET /api/appointments/{id}`, `PATCH /api/appointments/{id}/schedule` (move), `PATCH /api/appointments/{id}/complete` (mark as completed; accepts an optional JSON body `{"actualEnd": "..."}` and uses that timestamp for `actualEnd`, falling back to the current time when the body or the field is omitted), `PATCH /api/appointments/{id}/reopen` (revert the completed state), and `DELETE /api/appointments/{id}?scope=single|series` (the latter also removing every not-yet-past occurrence of a recurring series).
  - `PropertyController` — `GET /api/properties`, `GET /api/properties/{id}`, `POST /api/properties` (create), `PUT /api/properties/{id}` (update name/address/coordinates, keeping id and icon), `DELETE /api/properties/{id}` (delete, cascading to every appointment referencing that property) — see "Objects Overview" below.
  - `GeocodingController` — `GET /api/geocode?address=...`, proxied address resolution for the appointment map, and `GET /api/geocode/validate?street=...&houseNumber=...&postalCode=...&city=...`, structured address existence validation with a correction suggestion (see "Address Geocoding" below).
  - `GlobalExceptionHandler` — maps domain exceptions (`exception/`) to localized `404`/`409`/`400` responses, and a concurrent modification detected by JPA optimistic locking (`@Version`) to a localized `409`.
- **`dto/`** – Data Transfer Objects for exchanging data between backend and frontend, decoupled from the internal entities. Currently contains: `VersionResponse`, `ErrorResponse`, the appointment request/response DTOs (`CreateAppointmentRequest` — referencing its property by `propertyId` only, materials limited to non-blank entries of at most 255 characters, `MoveAppointmentRequest`, `AppointmentResponse` including `actualEnd`/`completed`, `HistoryEntryResponse`), `PropertyResponse` (including `latitude`/`longitude`), `CreatePropertyRequest` (`name`, `address`, optional `latitude`/`longitude`), `GeocodingResponse` (`latitude`/`longitude`, both `null` when no match was found), and `AddressValidationResponse` (`status` — `MATCH`/`SUGGESTION`/`NOT_FOUND`, coordinates for a `MATCH`, `suggestedStreet`/`suggestedHouseNumber`/`suggestedPostalCode`/`suggestedCity` for a `SUGGESTION`).
- **`config/`** – General application configuration. Currently contains: `CorsConfig` (CORS for the frontend dev server, origin configured via `remo.frontend.base-url`, allowing `GET`/`POST`/`PATCH`/`DELETE` on `/api/**`), `LocalizationConfig` (resolves the request locale from the `Accept-Language` header, falling back to English when no supported locale is requested), and `RestClientConfig` (provides the `RestClient.Builder` used by `GeocodingService`).
- **`service/`** – Business logic, transactional (`@Transactional`, read-only for lookups) so multi-row writes such as materializing a recurring series or deleting a property either fully succeed or are fully rolled back. Currently contains `AppointmentService`: validation (including that the referenced property exists), recurrence materialization (a recurring appointment eagerly creates a fixed horizon of 12 future occurrences sharing one `seriesId`, each independently movable/lockable/deletable), move with a locked-appointment guard, marking as completed (`complete`, sets `actualEnd` to `LocalDateTime.now()`) or reverting that (`reopen`, clears `actualEnd`), single-vs-series delete, and localizing each appointment's history log on read; `PropertyService`: listing (sorted by name), lookup by id, creation with a generated id and a fixed default icon (`pi-building`), update, and delete; and `GeocodingService` (see "Address Geocoding" below).
- **`repository/`** – Data access via Spring Data JPA. Currently contains `AppointmentRepository` (`findAllByOrderByStartAsc`, `findBySeriesId`) and `PropertyRepository` (`findAllByOrderByNameAsc`) — see "Persistence" below.
- **`entity/`** – JPA entities. Currently contains `Appointment` (including `actualEnd`, a derived `completed()` state, the mutators `reschedule`/`changeActualEnd` that also append a history entry, a lazy `@ManyToOne` reference to its `Property`, and materials stored as a PostgreSQL array), `HistoryEntry` (an `@Embeddable` record in the `appointment_history_entries` collection table, ordered by `sort_order`) and `HistoryEventType` (`CREATED`, `MOVED`, `COMPLETED`, `REOPENED`), and `Property` (`id`, `name`, `address`, `icon`, `latitude`, `longitude` — the coordinates are `null` while an address could not be geocoded — plus `updateDetails`). Both entities carry a `@Version` column for optimistic locking. An appointment no longer stores a copy of its property's name and address; `AppointmentResponse.propertyName`/`propertyAddress` are read from the referenced property, so editing a property is reflected in its appointments without any propagation step.
- **`exception/`** – Domain exceptions (`AppointmentNotFoundException`, `AppointmentLockedException`, `InvalidRecurrenceException`, `PropertyNotFoundException`) translated into HTTP responses by `GlobalExceptionHandler`.

### Objects Overview ("Objekte Auflisten")
`PropertyController`/`PropertyService`/`PropertyRepository` expose the same properties selectable when creating an appointment (`AppointmentPropertySelect.vue` on the frontend) as a list for the "Immobilien" page, plus a `POST /api/properties` create endpoint used by the pinned create card there, a `PUT /api/properties/{id}` update endpoint (`PropertyService.update` keeps the existing id and icon and overwrites name, address and coordinates) used by each card's edit button, and a `DELETE /api/properties/{id}` endpoint that also deletes every appointment referencing the property (via the `ON DELETE CASCADE` foreign key from `appointments.property_id`). A created property always gets the default icon `pi-building` (the create form has no icon field) and, unless the frontend already resolved coordinates via live geocoding while the form was open, `latitude`/`longitude` are stored `null` and resolved later through the same fallback the appointment map already uses. Open/completed appointment counts and each property's next appointment are not stored on `Property` itself; the frontend derives them from the already-loaded appointments (filtered by `propertyId`), so no aggregation endpoint was needed.

### Address Geocoding
`GeocodingService` resolves addresses to coordinates via the OpenStreetMap Nominatim API, for the appointment map on the frontend overview page (see `frontend/readme_frontend_en.md`). The call runs **server-side** instead of directly from the browser because Nominatim's abuse detection blocks requests lacking a real, application-identifying `User-Agent` header — one a browser can never set itself for security reasons. `RestClientConfig` provides the `RestClient.Builder` for this; `GeocodingService` sets a project-identifying `User-Agent` (pointing at the GitHub repository, no personal data), caches results per address in memory, and throttles new requests to one per second (Nominatim's usage policy). If the full address has no match, the service retries without a trailing city-district suffix (e.g. "Köln-Porz"), since Nominatim's free-text search otherwise fails on such addresses even though the street itself is real, and only then falls back to a structured search by the German postal code it contains. The frontend calls `GET /api/geocode` both as a fallback for properties without stored coordinates and live, debounced, while the "new property" form is open, to show a location preview before submitting.

`GeocodingService.validateAddress()` additionally checks, once on submit of the "new property" form (not on every keystroke, per Nominatim's rate limit), whether the entered street/house-number/postal-code/city combination really exists: a structured Nominatim search with all four fields (only attempted when the postal code is exactly 5 digits, skipped otherwise) is a `MATCH`, but only if Nominatim's own house number and postal code (when it returns them) agree with the ones entered — Nominatim's `postalcode` parameter is only a ranking hint, not a hard filter, and can return the real address with its actual (different) postal code despite a wrong one being entered, which without this check would have been wrongly accepted as a confirmed `MATCH`; if that has no result, a retry without the postal code that resolves to exactly one address, with a matching house number too, yields a `SUGGESTION` with that address's actual street, postal code and city (the common case: an otherwise-unique street with a typo'd postal code); anything else (no result even without the postal code, several results, or a disagreeing house number) is a generic `NOT_FOUND`, without a suggestion, since no single correction can be derived. `PropertyFormDialog.vue` blocks creation on anything but `MATCH` (see `frontend/readme_frontend_en.md`); this is enforced client-side only for now, since `CreatePropertyRequest` stores just the combined `address` string, not its structured components, so the server has nothing to re-validate against on `POST /api/properties`.

### `src/main/resources/`
Application configuration files: `application.yml` (Spring Boot configuration, incl. `spring.messages.basename`, `remo.frontend.base-url`, the local `spring.datasource` defaults and the JPA/Flyway settings), `db/migration/` (Flyway migrations, see "Persistence" below) and `locales/` (German/English translations for dynamic, server-generated text via Spring's `MessageSource`: `messages.properties`, `messages_de.properties`, `messages_en.properties`, resolved via `LocalizationConfig`; the base `messages.properties` bundle holds the English texts, matching the English fallback locale).

### Persistence
Properties and appointments are stored in PostgreSQL (replacing the former `ExampleObjects/`/`ExampleTerms/` JSON files; a fresh database starts empty, without seed data):

- **Schema:** all tables live in the dedicated schema `remo` (`spring.flyway.schemas`, `hibernate.default_schema`) rather than `public`, because Supabase automatically exposes `public` through its Data API. Tables: `properties`, `appointments` (foreign key `property_id` with `ON DELETE CASCADE`, indexes on `series_id`, `property_id` and `start_at`) and `appointment_history_entries`. Row Level Security is enabled on every table without any policy, so Supabase's API roles get no access, while the backend's owning database role is unaffected.
- **Migrations:** Flyway owns the schema (`src/main/resources/db/migration/V<n>__*.sql`, applied automatically on startup); Hibernate only validates it (`ddl-auto: validate`). Never edit an already applied migration, add a new `V<n+1>__...sql` instead.
- **Local development:** `docker compose up -d` in `backend/` starts PostgreSQL 17 (`docker-compose.yml`), matching the defaults in `application.yml` (`jdbc:postgresql://localhost:5432/remo`, user/password `remo`), so `mvn spring-boot:run` needs no further configuration.
- **Production (Supabase project "RemoDB"):** the backend on the Oracle Cloud instance reads `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME` and `SPRING_DATASOURCE_PASSWORD` from the environment (see `.env.example`). Use Supabase's **Session pooler** connection (IPv4-reachable, port 5432, user `postgres.<project-ref>`, `?sslmode=require`), not the direct connection (IPv6-only) nor the transaction pooler (port 6543, incompatible with Hibernate's server-side prepared statements). The deploy workflow writes these values from the GitHub secrets `REMO_DB_URL`, `REMO_DB_USERNAME` and `REMO_DB_PASSWORD` into `backend.env` (mode `600`) next to the deployed jar; the backend's systemd unit loads it via `EnvironmentFile=`. If the database is unreachable, Flyway fails on startup and the deploy's health check fails.
- **Tests:** repository, service and controller tests run against a throwaway PostgreSQL 17 container (Testcontainers, `TestcontainersConfiguration`), so `mvn test` requires a running Docker daemon.

### `src/test/java/...`
JUnit tests, structure mirrors `src/main/java/...`. Covers the version/localization/CORS config and the full appointment, property, and geocoding features (repository, service, controller), with every Spring context backed by a Testcontainers PostgreSQL instance (Docker required) — see `CLAUDE.md`, section "Tests".

### `pom.xml`
Dependencies and build configuration (Maven). Holds the single source of truth for the application version (`<version>`), surfaced to the frontend via `GET /api/version`.
